## 03. 1.1.1 使命 · 让心里有故事的人，写出一部属于自己的自洽长篇

- 使命：把「创作一部长篇」的门槛，从「会不会写」降到「说不说得清一个想法」；把「记得住」交给系统，而不是交给更长的提示词。
- 门槛
- 读者只要给得出题材、主角和走向，就能拿到第 1 章；不需要学写作，也不需要学提示词。
- 质量
- 跨章一致性靠结构化事实来管：每个设定带版本、变更理由和正文出处，可以逐条核验。
- 归属
- 作品文件存在本机，可以导出；不为平台锁定，也不为订阅付费。
- 依据：docs/requirements/problem_definition.md（问题定义与产品描述）

## 04. 1.1.2 口号 · 对外一句记得住的话，对内一句不许走偏的话

- 主口号（对外）
- 一个点子，一部自洽的长篇。
- 副口号（对内 / README 首行）
- 先把「记得住」做对，再谈「写得好」。
- 备选（按场景取用）
- 「想看的，自己写出来。」——面向读者，情绪最直接
- 「不会写，也能写完。」——强调完成度，适合首屏
- 「设定不丢，故事才长。」——强调一致性，适合技术读者

## 05. 1.1.3 目标用户 · 用户是「想创作却不会写」的读者，不是专业作者

- 爱看小说的普通人
- 有明确口味：题材、主角、CP、爽点都在心里，就是写不出来。
- 诉求：一个点子，先拿到第 1 章看看合不合口味。
- 「设定控」读者
- 对前后一致、伏笔回收特别敏感，受够了 AI 的「吃设定」。
- 诉求：能查到某个设定从哪一章开始、又在哪一章改变。
- 短视频 / 图文创作者
- 需要设定自洽、可以直接改的故事脚本，但自己不会写小说。
- 诉求：题材能定制，产物能直接编辑和导出。
- 这一版明确不服务谁
- 专业作者的量产工具（AI 文笔还撑不起量产质量）｜ 多人协作团队 ｜ 移动端与在线账号（首版单用户、本地运行）
- 市场口径（估算，非统计口径）
- TAM 网文读者 5.75 亿
- SAM 愿尝试 AI 创作为 0.5%–2% → 约 290 万–1150 万
- 种子 首年 100–500 名真实读者
- 用户判据：一个没写过小说的人，10 分钟内能不能拿到一部属于自己口味的第一章？
- 数据来源：《2024 中国网络文学蓝皮书》（2025-06）；SAM / SOM 为基于公开总量的比例假设，需实测校准。

## 06. 1.1.4 如何获得用户 · 从 0 到 1000：种子、内容、口碑三步走

- 0 → 100
- 种子：先把身边人变成用户
- · 课程、社团、写作群内测邀请
- · 现场做「同题材对照生成」演示
- · 每位受邀者试读并填反馈表
- 看板指标：首章读完率 / 二次生成率
- 100 → 1000
- 内容：把「吃设定」做成可复现的案例
- · 同题材、同模型，有无状态记忆对比
- · B 站 / 知乎 / 小红书 + README 作信任入口
- · 开源仓库即试用入口，一条命令跑通
- 看板指标：仓库访问 → 本地跑通率
- 1000 →
- 口碑：作品本身是最好的广告
- · 每部作品可导出、可分享首章
- · 读者晒「我生成的小说」，带作品名回链
- · 把对照实验更新成季度报告
- 看板指标：自然分享带来的新增
- 三个必须做对的转化点
- ① 生成前看得见费用（预估 token 与人民币）　② 失败能续（检查点恢复，不从头再来）　③ 首章就能判断合不合口味（先读再批量）
- 说明：获客路径为计划，尚未实测；种子目标 100–500 人，指标口径随第一轮试用校准。

## 09. 1.2 产品定义 · 用定位模板把产品说清楚：给谁、解决什么、凭什么不同

- 对于
- 心里有想看的题材、却不会写小说的普通读者
- 他们
- 想让 AI 把想法写成一部前后连贯的长篇，但通用 AI 一写长就「吃设定」
- Tome Agent 是一个
- 本地运行的长篇小说生成助手
- 它能够
- 用「逐章规划 → 正文 → 事实变更 → 独立审核 → 原子提交」维护带出处和版本的记忆，生成可暂停、可恢复、可导出
- 不同于
- 面向作者的复杂写作工作台，也不同于记不住设定的通用 AI 聊天
- 我们的产品
- 让不会写小说的人，也能创作出一部设定自洽、属于自己的长篇小说

## 10. 1.2.1 解决的问题 · 五个症状，一个根因：记忆能力撑不起一部书

- 01
- 记不住设定
- 年龄、关系、能力、地点——稍微写长一点就开始前后矛盾。
- 02
- 时间线与因果对不上
- 事件顺序、谁在场、发生过什么，跨章之后对不齐。
- 03
- 伏笔与义务不回收
- 前面埋下的线索、答应过的走向，后面忘了提。
- 04
- 上下文不可持续
- 全文塞进长上下文：贵、注意力衰减；改成摘要：细节又丢了。
- 05
- 生成过程不可恢复
- 一次失败就要重来，成本和进度一起损失。
- 根因判断
- 「记忆能力」≠「上下文长度」
- 模型不是不想记。是「把前文再喂一遍」这种记忆方式，撑不起一部书——越往后越贵、越模糊。
- 所以我们不从「再写一段更长的提示词」入手，而从「怎么让故事状态可查、可验、可恢复」入手。
- 「状态记忆能减少跨章矛盾」目前是待验证假设：用同输入、同模型、有 / 无记忆的对照实验来证明。

## 11. 1.2.2 对客户的价值 · 用用户故事说价值：作为谁、完成了什么、带来什么

- 作为
- 只想看自己想看故事的读者
- 完成 用一两句话描述题材、主角和走向，生成并读完第 1 章
- 带来 不必等更新，也不必迁就平台现成的套路
- 作为
- 在意前后一致的连载读者
- 完成 每章后看到人物与物品的关键设定、版本，以及它从哪章开始、哪章改变
- 带来 后文沿用同一设定，矛盾当场被指出
- 作为
- 业余写作者
- 完成 为一部作品填写文风要求与参考片段，设定从下一章开始生效
- 带来 后续章节保持相近口吻，已经写好的正文不变
- 作为
- 想一次写完多章的作者
- 完成 设好目标章节数与字数，连续生成并在目标处停下
- 带来 一口气拿到多章初稿，并知道写到哪里、为什么停下
- 每条故事配 Gherkin 验收条件，见 docs/requirements/user_stories.md（按 INVEST 拆分，共 5 条）。

## 12. 1.2.3 解决方案 · 形态选「本地网站」：作品和密钥留在本机，浏览器打开就能用

- 为什么是网站，不是小程序 / App：作品文件与 API Key 必须留在本机、成本按 token 透明、不经过上架审核；本地网页用浏览器即可打开，不需要账号、不需要装客户端。
- 技术组成（版本见 README）
- 界面
- Vue 3.5.44 内置运行时，无前端构建；本地服务 http://127.0.0.1:8765
- 编排
- LangGraph 1.2.17 把五个阶段建成状态图，支持条件分支与重规划
- 存储
- 文件模式零配置即可跑；需要持久化时用 PostgreSQL 17 + Psycopg 3.3.3
- 模型
- Chat Completions 兼容接口：DeepSeek、OpenAI 及其他兼容服务
- 用户看到的三件事
- · 生成前：显示本次预估输入 / 输出 token 与人民币费用，确认后才调用模型
- · 生成中：逐章保存检查点，中断后从断点继续，正式稿只在整章校验通过后写入
- · 生成后：在工作台读章、导出排版好的 Markdown，作品目录在本机随手可备份
- 对应课程要求「网站 / 微信小程序 / Android 应用」中的「网站」形态。

## 13. 1.2.3 解决方案 · 运行机制 · 一章是怎么生成的：五个阶段，一次事务提交

- 下一章规划
- 只改下一章
- 正文候选
- 不能改存档
- 事实变更候选
- 带出处与版本
- 独立审核
- 矛盾与遗漏
- 整章事务提交
- 失败不改正式稿
- 导出 Markdown
- 可改可投稿
- 不越权
- 规划只提下一章计划；写作角色不能直接改正式存档；审核角色只判不改。
- 可追溯
- 每条事实带稳定属性名、版本、变更理由和正文原句，能查到某个设定从哪一章开始、又在哪一章改变。
- 可恢复
- 先在副本上校验章节、计划与记忆，通过后整章提交；失败不改变正式快照，中断后从检查点继续。
- 一次生成 = 「规划 → 写作 → 记忆 → 审核 → 提交」；本地运行、作品留在本机、按 token 透明计费。

## 14. 十二条原则，一条主线：每条都要能在仓库里找到证据

- 01
- 需求 · 信息 · 创新
- 先有真需求，再用信息校准，最后才谈创新
- 02
- 系统 · 收敛 · 优化
- 把作品当系统，先发散后收敛，再逐项优化
- 03
- 继承 · 效益 · 时间
- 能继承的不重造，算清效益，抢住窗口
- 04
- 定量 · 简化 · 审核
- 能测就测，能简就简，每一步都审
- 为什么是这十二条：它们来自产品设计的基础原则体系（需求 / 信息 / 创新；系统 / 收敛 / 优化；继承 / 效益 / 时间；定量 / 简化 / 审核），正好覆盖我们这轮设计要做判断的四个层面——要不要做、怎么成形、拿什么换、怎么验收。
- 参考：产品设计小文集锦（四篇）；机械工业出版社《现代产品设计指南》1.5 节产品设计和开发的原则。

## 15. 需求定方向，信息校准方向，创新才有落脚点

- 需求原则
- 功能要求来自客观需求：显需求推动改进，隐需求催生创新。
- 本产品的做法
- · 需求从「不会写」和「吃设定」出发，不是从「模型能干什么」出发
- · 先冻结 MVP：单用户、本地、中文、顺序逐章；多人协作 / 移动端 / 自动出版明确不做
- · 显需求 = 把想法变成第 1 章；隐需求 = 设定可查、失败可续
- 信息原则
- 全面、充分、正确、可靠地掌握市场、技术、测试信息，用它引导设计。
- 本产品的做法
- · 设计前完成竞品与长文本架构调研：网文读者 5.75 亿、三类竞品对照、长上下文 / 摘要 / 检索方案比较
- · 结论「记忆能力是真实短板」写进问题定义，而不是拍脑袋定功能
- · 调研、架构、验证记录都进仓库，成为下一轮决策的输入
- 创新原则
- 大胆创新，冲破传统观念与惯例的束缚。
- 本产品的做法
- · 事件先行：先推演场景事件与状态，再写正文，而不是写完再回头猜关键事实
- · 事实账本：每条设定带稳定属性名、版本、变更理由和正文原句
- · 提交是事务不是覆盖：在副本上校验通过才整体写入
- 一句话：需求回答「该不该做」，信息回答「凭什么这样设计」，创新回答「我们做了什么别人没做的」。

## 16. 把作品当系统设计，先发散后收敛，再逐项优化

- 系统原则
- 用系统论方法求功能结构，通过分析、综合与评价，达到综合最优。
- 本产品的做法
- · 写作被建成「规划—写作—记忆—审核—提交」的状态系统，用 LangGraph 状态图表达
- · 四个角色职责与 JSON 契约固定：规划只改下一章、写作不能改存档、审核只判不改
- · 任何环节失败都不污染正式快照——系统边界优先于单点效果
- 收敛原则
- 先发散思维构思方案，再综合多种信息收敛。
- 本产品的做法
- · 记忆方案先发散四种：全文塞上下文 / 摘要压缩 / 向量检索 / 结构化事实
- · 按「可核验、可恢复、成本」三个标准收敛到结构化事实 + 三层记忆
- · 首版只带最近两章、最多 128 条有效事实：先收敛到能验证的规模
- 优化原则
- 方案择优、参数优化、总体方案优化：高效、优质、经济。
- 本产品的做法
- · 篇幅按「总字数 − 已写 − 剩余章节」动态分配，而不是每章固定字数
- · 局部失败降级：规划或记忆处理失败时记录问题，尽量保住有效正文
- · 审核格式错误最多修一次，避免无限循环；重规划只改尚未写作的章节
- 一句话：系统原则让我们定义务边界，收敛原则让我们砍掉炫技方案，优化原则让我们在真实约束下调参数。

## 17. 能继承的不重造，算清效益，抢住时间窗口

- 继承原则
- 批判地吸收前人成果，推陈出新，为我所用。
- 本产品的做法
- · 编排用 LangGraph、接口用 Chat Completions 兼容协议、界面用 Vue 运行时、存储用 PostgreSQL
- · 继承的是成熟模式：状态图、事务提交、检查点恢复、幂等回执
- · 不继承的是形态：不复制「面向作者的复杂写作工作台」那一套功能堆叠
- 效益原则
- 既讲技术经济效益，也讲社会效益。
- 本产品的做法
- · 本地运行 + 自带 Key + 按 token 计费，生成前显示预估人民币费用
- · 单用户本地存档，省掉服务器与运维成本；换机器只要拷作品目录
- · 社会效益：降低创作门槛，作品留在作者手里，可导出、不被平台锁定
- 时间原则
- 加快研制节奏，并预测同类产品在开发期可能发生的变化。
- 本产品的做法
- · 14 天交付计划：需求冻结 → 原型联调 → 真实模型 → 对照修复 → 交付演练
- · 窗口期判断：通用模型记忆能力在增强，所以必须尽早用可复现对照实验证明价值
- · 先交付能演示的最小闭环，把「更好文笔」留给模型升级，而不是自己造
- 一句话：继承省时间，效益定取舍，时间定顺序——三者一起决定了我们的两周计划长什么样。

## 18. 能测就测，能简就简，每一步都审

- 定量原则
- 在方案选择、性能评价、效益评价上尽量采用科学的定量方法。
- 本产品的做法
- · 成功标准写成可测指标：约 1 万字 / 8–10 章、跨章矛盾数对比基线、token 与费用、恢复成功率
- · 回归测试 127 项（120 通过、7 项无数据库时跳过）+ 长篇引擎 42 项
- · 用户测试表逐项打分，试读问卷量化「愿不愿意读完」
- 简化原则
- 保证功能的前提下力求简化，降低成本、保证质量。
- 本产品的做法
- · 后端用 Python 标准库 http.server，不额外引入 Web 框架
- · 前端用内置 Vue 运行时，零构建步骤；文件模式零配置即可运行
- · 首版只做中文 + 顺序逐章 + 单用户，把复杂度留给后续迭代
- 审核原则
- 随时审核每个设计步骤的信息，确保每一步正确。
- 本产品的做法
- · 每章一个独立审核角色：查硬矛盾、因果问题和重要记忆遗漏，只判不改
- · 提交前在副本上整体校验章节、计划与记忆；PR 必须由另一名成员审阅
- · 代码走 ruff 等质量检查，密钥与作品数据不得进入 Git
- 落点：十二原则最终收敛成一句话——先把「记得住」做对，再把「写得好」交给模型迭代。
