# Tome Agent 团队计划

## 一、协作方式

- `main`：可运行、可演示的稳定版本。
- `develop`：日常集成分支；功能分支从这里建立并通过 Pull Request 合并。
- 功能分支：`feature/简短名称`；修复分支：`fix/简短名称`；文档分支：`docs/简短名称`。
- 每项工作先建 GitHub Issue，写清负责人、验收条件和目标日期；提交或 PR 使用 `#编号` 关联 Issue。
- 另一名成员完成审阅后再合并；紧急修复也要保留 Issue 和测试记录。

> 成员 A–D 是当前占位称呼。确定名单后替换为真实姓名和 GitHub 用户名。

## 二、四人分工

| 角色 | 主要负责人 | 主要任务 | 交付物 |
| --- | --- | --- | --- |
| 产品与写作设计 | 成员 A | 用户需求、小说工作流、提示词与演示故事 | 问题定义、验收场景、示例作品 |
| 核心引擎 | 成员 B | INF 四角色调度、故事记忆、存档 | `code/core_engine/inf_writer/` 核心模块及单元测试 |
| 前端与集成 | 成员 C | DeepSeek 接入、应用服务、后续界面与导出 | `code/backend/inf_backend/`、前端及集成测试 |
| 测试与项目管理 | 成员 D | Issue/Kanban、测试、文档、演示材料 | 测试记录、风险表、版本发布资料 |

每项关键功能至少由一名非负责人复核，避免只有一个人了解模块。

## 三、两周快速交付计划

| 阶段 | 时间 | 目标 | 完成标准 |
| --- | --- | --- | --- |
| 需求与基线 | 第 1–2 天 | 冻结 MVP；准备相同输入的普通摘要续写基线 | 5W1H、产品范围、评测指标已评审 |
| 原型联调 | 第 3–5 天 | 四角色逐章生成、记忆、审核和存档贯通 | 本地模拟测试全部通过 |
| 真实模型验证 | 第 6–8 天 | 使用 DeepSeek 完成小规模试写，再进行约 1 万字实验 | 保存模型配置、token、成本与失败记录 |
| 对照与修复 | 第 9–11 天 | 比较基线和 Tome，修复阻断演示的问题 | 两名成员完成一致性复核，严重缺陷关闭 |
| 交付准备 | 第 12–14 天 | 完善文档、演示脚本、PPT与仓库 | 新电脑安装演练成功，8 分钟演示可完成 |

## 四、Issue 工作流

1. `Todo`：需求已记录，尚未开始。
2. `In Progress`：已有负责人和分支，正在开发。
3. `Review`：代码或文档完成，等待同伴检查。
4. `Done`：验收条件满足、相关测试通过、资料已合并。
5. 缺陷使用 Bug 报告模板；至少填写复现步骤、期望结果、实际结果和环境。

## 五、每周检查

- 每日异步更新 Issue；阻塞问题当天说明。
- 每周至少一次 20 分钟会议：同步进度、风险、下一步和需要协助的事项。
- 周末检查仓库链接、Kanban、打开的 Issue、测试状态和演示风险。
- 沟通内容和风险跟踪频率见[沟通与风险管理计划](COMMUNICATION_AND_RISK_PLAN.md)。
