# Tome Agent 风险管理计划

> 本文档定义 Tome Agent 项目的风险管理方法、风险识别与评估、应对策略、监控跟踪与升级机制。以下风险均为可能发生的事件，并非已发生的问题；概率与影响为项目初期的判断，测试后根据实际情况调整。

## 一、目的与范围

本计划用于识别、评估、应对和监控项目过程中可能影响"可运行、可恢复、可演示"交付目标的不确定性，覆盖资源、项目管理、外部因素、技术和进度五个维度，并将高影响风险优先纳入处理。风险管理的目标是提前发现并降低负面影响，同时利用有利机会。

## 二、风险管理方法

风险管理遵循五步闭环流程，循环执行：

1. **识别**：结合需求、设计、开发和验证各环节，持续发现潜在风险，记入风险登记册。
2. **评估**：按概率与影响两个维度对风险定性，确定优先级。
3. **应对**：为每项风险指定应对策略、具体措施、负责人和跟踪频率。
4. **监控**：按频率跟踪风险状态，观察预警信号，必要时调整评估。
5. **更新**：已发生的风险转为具体问题跟踪；已缓解的风险记录原因与验证结果后关闭。

## 三、概率与影响定义

| 等级 | 概率（发生可能性） | 影响（对交付目标的影响程度） |
| --- | --- | --- |
| 高 | 很可能发生（>50%） | 导致交付延期、核心功能不可用，或造成严重费用/数据损失 |
| 中 | 可能发生（10%–50%） | 影响部分功能、增加返工，需要额外协调或工作量 |
| 低 | 不太可能（<10%） | 轻微影响，可快速解决，不影响关键路径 |

**优先级判定：** 高×高、高×中、中×高为**高**优先级；中×中、高×低、低×高为**中**；其余为**低**。机会类风险单独标注，按"利用"策略处理。

| 编号 | 风险名称 | 维度 | 概率 | 影响 | 优先级 | 风险说明与预警信号 |
| --- | --- | --- | --- | --- | --- | --- |
| R1 | 成员开发经验不足 | 资源 | 高 | 高 | 高 | 环境配置、调试或协作中反复遇到困难，返工与学习时间明显增加 |
| R2 | 模型调用预算不足 | 资源 | 中 | 高 | 高 | token 消耗快速上升，余额不足以支撑后续测试与演示 |
| R3 | 分工与接口约定不清 | 项目管理 | 中 | 中 | 中 | 任务遗漏或重复，模块间无法顺利集成 |
| R4 | API Key 或作品数据泄露 | 项目管理 | 中 | 高 | 高 | 密钥或正文出现在截图、日志、群聊或仓库中，产生费用损失或内容泄露 |
| R5 | 需求持续扩张 | 项目管理 | 高 | 高 | 高 | 临时新增登录、多模型、复杂编辑等功能，挤占核心流程开发时间 |
| R6 | DeepSeek 服务或网络异常 | 外部因素 | 中 | 高 | 高 | 限流、超时、余额或接口变化导致生成中断，影响测试与演示 |
| R7 | 模型工具调用不稳定 | 技术 | 高 | 高 | 高 | 模型返回错误参数、无效引文或无法完成状态更新，章节不能提交 |
| R8 | 长文本连贯性不足 | 技术 | 高 | 高 | 高 | 跨章出现人物、时间、物品状态矛盾，或情节重复、推进停滞 |
| R9 | 存档与恢复异常 | 技术 | 中 | 高 | 高 | 异常退出、文件损坏或错误恢复造成进度丢失、正文与记忆不一致 |
| R10 | 不同电脑安装失败 | 技术 | 中 | 高 | 高 | Python 版本、依赖或系统环境差异导致同伴无法启动软件 |
| R11 | 交付准备时间不足 | 进度 | 高 | 高 | 高 | 开发或修复超时，压缩文档、部署和答辩演练时间 |
| R12 | AI 工具提效机会未充分利用 | 项目管理 | 高 | 中（正面） | 机会·高 | 未使用 AI 辅助编码、测试设计与文档整理，错过提前完成与增加验证时间的机会 |
| R13 | 关键成员缺席或单点知识 | 资源 | 中 | 高 | 高 | 某模块只有一名成员了解，成员请假或离开时无人接手 |
| R14 | 模型输出内容质量与合规 | 技术 | 中 | 中 | 中 | 生成内容出现事实错误或不合适内容，需人工审核修正 |
| R15 | 演示现场环境或网络异常 | 外部因素 | 中 | 高 | 高 | 演示设备、网络或软件版本与开发环境不一致，导致现场演示中断 |

## 五、风险应对计划

应对策略：**规避**（消除风险源）、**减轻**（降低概率或影响）、**转移**（转移给第三方）、**接受**（保留并观察）、**利用**（放大机会）。

| 编号 | 风险名称 | 应对策略 | 应对措施 | 负责人 | 跟踪频率 |
| --- | --- | --- | --- | --- | --- |
| R1 | 成员开发经验不足 | 减轻 | 提供统一安装说明和示例；任务拆小；关键操作结对完成；每人熟悉至少一条完整使用流程 | 查军益 | 每日 |
| R2 | 模型调用预算不足 | 减轻 | 先短篇幅、小批量测试；设置请求与 token 上限；记录用量；扩展测试前评估预算 | 查军益 | 每次真实调用后 |
| R3 | 分工与接口约定不清 | 减轻 | 每项任务指定负责人和验收条件；修改公共接口前通知相关成员；关键改动交叉复核 | 查军益 | 每日 |
| R4 | API Key 或作品数据泄露 | 规避 | 使用本地 `.env`；配置 Git 忽略规则；提交前检查文件；发生泄露立即撤销密钥并更换 | 秦宗鑫、周涛 | 每次提交与分享前 |
| R5 | 需求持续扩张 | 规避 + 减轻 | 冻结首版范围（规避）；新增需求先评估成本；优先保证大纲、生成、记忆、恢复和导出可用（减轻） | 查军益 | 每次需求变更时 |
| R6 | DeepSeek 服务或网络异常 | 减轻 | 保存成功章节和失败记录；限制重试；保留可恢复进度；答辩准备本地样例与录屏 | 秦宗鑫、谭钧浩 | 异常时即时跟踪 |
| R7 | 模型工具调用不稳定 | 减轻 | 使用明确工具规范与程序校验；保留失败反馈；先验证三章闭环再扩大篇幅；防止无限循环 | 秦宗鑫、谭钧浩 | 每轮集成测试 |
| R8 | 长文本连贯性不足 | 减轻 | 使用冻结大纲、当前状态和相关前文；建立人工评阅清单；按实际错误调整提示与记忆策略 | 查军益、秦宗鑫 | 每批生成后 |
| R9 | 存档与恢复异常 | 减轻 | 采用原子保存与版本校验；分开保存正式状态和失败工作副本；测试异常退出及恢复；定期备份 | 秦宗鑫、周涛 | 每次相关改动后 |
| R10 | 不同电脑安装失败 | 减轻 | 固定依赖版本；使用独立环境；至少一名未参与开发的成员按文档从零安装 | 周涛 | 每次发布前 |
| R11 | 交付准备时间不足 | 减轻 | 每日检查关键任务；优先交付最小闭环；提前准备说明和演示素材；预留最后一个工作日验证与演练 | 查军益、谭钧浩 | 每日 |
| R12 | AI 工具提效机会未充分利用 | 利用 | 用于代码草稿、测试建议和文档整理；由成员检查并实际运行；节省的时间用于交叉测试和创作质量评估；目标：提前 1–2 个工作日完成首版闭环 | 全体成员 | 每日 |
| R13 | 关键成员缺席或单点知识 | 减轻 | 关键模块文档化；安排交叉复核；定期在团队内讲解各自模块，避免单点知识 | 查军益 | 每周 |
| R14 | 模型输出内容质量与合规 | 减轻 | 正文最终由作者审核；加入敏感/不合适内容检查；在文档中明确模型输出需人工复核 | 秦宗鑫 | 每批生成后 |
| R15 | 演示现场环境或网络异常 | 减轻 | 准备本地离线样例和演示录屏；提前到现场测试环境；制定现场应急预案（切换到录屏或本地缓存） | 周涛 | 交付演练与演示前 |

## 六、风险监控与跟踪

- 风险台账每日同步一次，更新风险状态、负责人及下一步行动。
- 风险状态分为：**待观察、处理中、已缓解、已发生、已关闭**；已发生的风险转为具体问题跟踪，不能只停留在风险描述。
- 高优先级风险进入日常同步；中低优先级风险在周会中复查。
- 处理完成后记录原因、措施和验证结果，并更新安装说明、测试用例或应急方案。

## 七、风险升级与报告

触发以下任一情形，先按[沟通管理计划](communication_mgmt_plan.md) L3 即时上报全体成员，再执行下表处置动作。

| 情形 | 处置动作 | 响应时限 |
| --- | --- | --- |
| 密钥泄露 | 撤销并更换密钥，排查泄露范围 | 即时 |
| 正式存档损坏 | 暂停生成，启用备份恢复 | 即时 |
| 核心生成流程持续失败 | 定位并优先修复，必要时回退到上一可用版本 | 即时 |
| 高优先级风险临近触发 | 由负责人当天上报，项目协调人组织评估应对 | 当天 |

## 八、应急与回退方案

- **模型不可用**（对应 R6）：切换到本地模拟/离线样例演示，保留已生成正文与录屏作为答辩素材。
- **存档损坏**（对应 R9）：从正式存档的备份副本恢复；无法恢复时，用失败工作副本重建并重新生成受影响章节。
- **现场演示异常**（对应 R15）：优先展示录屏和本地样例，讲解流程与证据链，不依赖实时网络。
- **依赖安装失败**（对应 R10）：使用已装好的 `.venv` 或锁定版本重新安装，必要时由已完成安装的成员协助排查。

## 九、计划评审与更新

- 风险台账在每次周会中更新一次；真实模型测试后，根据实际用量（沿用 R2 每次真实调用后的用量记录）、失败率和连贯性表现，重新评估 R2、R6、R7、R8 的概率与影响。
- 新的风险在发现时即时登记，不再等周会。
- 沟通相关的渠道、频度与升级规则见[沟通管理计划](communication_mgmt_plan.md)。
