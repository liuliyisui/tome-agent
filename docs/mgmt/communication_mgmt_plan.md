## 一、项目概况与干系人

**项目目标：** 基于 DeepSeek 模型，实现故事规划、逐章生成、跨章状态记忆、断点续写和小说导出，形成可运行、可演示的软件作品。

| 干系人 | 角色 | 主要沟通关注点 | 参与方式 |
| --- | --- | --- | --- |
| 查军益 | 核心引擎与集成 | 生成框架、模型接口、代码集成的进度与接口约定 | 开发、评审、技术决策 |
| 秦宗鑫 | 项目协调与质量 | 需求范围、进度、创作质量评估、风险统筹 | 会议主持、需求与评审 |
| 谭钧浩 | 测试与问题跟踪 | 环境安装、功能测试、缺陷复现与跟踪 | 测试、缺陷记录 |
| 周涛 | 页面与文档展示 | 页面体验、文档整理、成果展示与演示 | 页面、文档、演示 |
| 指导教师 / 答辩评委 | 评审 | 项目进度、成果证据链、演示效果 | 阶段性汇报与答辩 |
| 外部试用用户 | 试用用户 | 安装与使用体验、缺陷反馈 | 试用反馈（问卷/群） |

## 二、沟通目标与原则

1. **信息同步**：确保每位成员对需求、进度、接口和风险有共同理解。
2. **决策可追溯**：影响需求、接口、进度的决定必须形成文字记录，落到 Issue 或文档。
3. **问题及时暴露**：阻塞问题和关键风险当天上报，不积压。
4. **安全可控**：API Key 与作品数据不在非授权渠道传播。
5. **最小闭环优先**：沟通围绕"可运行、可恢复、可演示"的最小交付目标展开。

## 六、沟通执行规则

1. 每日同步围绕"已完成、下一步、遇到的阻碍"展开。
2. 缺陷记录必须包含运行环境、操作步骤、预期结果和实际结果，必要时附脱敏截图或日志。
3. 影响核心生成流程、数据安全或交付时间的问题由发现人即时报告，负责人组织处理。
4. 需求变更先评估工作量和对交付的影响，再决定本次实现或延期，避免临近提交不断增加功能。
5. 代码通过分支和 Pull Request 协作，合并前由另一名成员检查；关键文档与代码同步更新。
6. API Key 不在群聊、截图、日志或仓库中传播；分享测试数据前检查是否包含敏感信息。

## 七、信息发布、存档与保密

- 正式结论（需求、接口、设计决策）写入仓库 `docs/` 或 Issue，作为唯一权威来源。
- 会议纪要与行动项由主持人记录，发送到群并在 Issue 中登记责任人。
- 代码与文档通过 Git 版本管理；发布版本打标签留痕。
- 密钥只保存在本地 `.env`，不提交仓库；作品与运行数据位于 `data/`，同样不入库。
- 测试与演示数据分享前脱敏，去除密钥、真实用户信息与未公开正文。

## 八、问题升级机制

| 级别 | 触发条件 | 处理方式 | 响应时限 |
| --- | --- | --- | --- |
| L1 日常 | 一般任务、非阻塞缺陷 | 负责人自行处理，记录到 Issue | 当天 |
| L2 团队决策 | 影响需求、接口、进度或需要跨模块协调 | 项目协调人召集，形成决策记录 | 一个工作日内 |
| L3 紧急 | 密钥泄露、正式存档损坏、核心生成流程持续失败 | 立即通知全体成员并暂停相关操作 | 即时 |

L2 需跨模块协调与召集，故响应时限放宽至一个工作日。

## 九、计划评审与更新

- 沟通计划由项目协调人在每次周会时检查一次，确认渠道、频度与责任是否仍然适用。
- 干系人、分工或工具发生变化时，同步更新本文档及[团队计划](TEAM_PLAN.md)。
- 风险相关的识别、评估与应对见[风险管理计划](risk_mgmt_plan.md)。
