## 1.1.1 使命

**让心里有故事的人，写出一部属于自己的自洽长篇。**

拆成三件事：

- **门槛**：从「会不会写」降到「说不说得清一个想法」。读者只要给得出题材、主角和走向，就能拿到第 1 章。
- **质量**：跨章一致性交给结构化事实管理——每个设定带版本、变更理由和正文出处，可以逐条核验。
- **归属**：作品文件存在本机，可以导出，不为平台锁定，也不为订阅付费。

## 1.1.2 口号

- **主口号（对外）**：一个点子，一部自洽的长篇。
- **副口号（对内 / README 首行）**：先把「记得住」做对，再谈「写得好」。
- 备选：想看的，自己写出来／不会写，也能写完／设定不丢，故事才长。

## 1.1.3 目标用户

用户是**想创作却不会写**的读者，不是专业作者。

1. **爱看小说的普通人**——有明确口味（题材、主角、CP、爽点），就是写不出来。诉求：一个点子，先拿到第 1 章看看合不合口味。
2. **「设定控」读者**——对前后一致、伏笔回收敏感，受够了 AI 的「吃设定」。诉求：能查到某个设定从哪一章开始、又在哪一章改变。
3. **短视频 / 图文创作者**——需要设定自洽、可直接改的故事脚本。诉求：题材可定制，产物可编辑可导出。

这一版明确不服务：专业作者的量产工具、多人协作团队、移动端与在线账号（首版单用户、本地运行）。

市场口径（估算，非统计口径）：网文读者 5.75 亿（《2024 中国网络文学蓝皮书》，2025-06）；愿尝试 AI 创作的比例按 0.5%–2% 估算约 290 万–1150 万；首年种子用户目标 100–500 人。

用户判据：一个没写过小说的人，10 分钟内能不能拿到一部属于自己口味的第一章？

## 1.1.4 如何获得用户

| 阶段 | 做法 | 看板指标 |
| --- | --- | --- |
| 0 → 100 | 课程、社团、写作群内测邀请；现场做「同题材对照生成」演示；每位受邀者试读并填反馈表 | 首章读完率 / 二次生成率 |
| 100 → 1000 | 把「吃设定」做成可复现案例（同题材、同模型、有无状态记忆对比）；B 站 / 知乎 / 小红书 + 仓库 README 作信任入口 | 仓库访问 → 本地跑通率 |
| 1000 → | 每部作品可导出、可分享首章；读者晒「我生成的小说」，带作品名回链 | 自然分享带来的新增 |

三个必须做对的转化点：生成前看得见费用、失败能续（检查点恢复）、首章就能判断合不合口味。获客路径为计划，尚未实测。

## 1.1.5 团队优势

四个人是一条完整链条：开发（查军益）→ 创作与质量评估（秦宗鑫）→ 环境与功能测试（谭钧浩）→ 体验与成果文档（周涛）。每项交付至少一名非负责人复核。

- **链条完整**：避免「一个人测自己写的代码」。
- **视角对**：计算机专业背景，从「数据一致性、事务、可恢复」切入长文本生成，而不是从「提示词技巧」切入。
- **可复现**：两周计划、Issue / Kanban 留痕、真实调用记录 token 与费用；换一台电脑能按脚本跑起来。

## 1.1.6 如何做到差异化

| 维度 | 通用 AI 聊天 | 面向作者的写作工具 | 网文阅读平台 | Tome Agent |
| --- | --- | --- | --- | --- |
| 目标用户 | 会用提示词的任何人 | 会写的作者 | 读者（读现成的） | 想创作却不会写的读者 |
| 输入方式 | 一段提示词 | 大纲、设定、章节指令 | — | 一个点子：题材 + 主角 + 走向 |
| 记忆方式 | 上下文窗口，越长越贵、越衰减 | 多为摘要或设定表 | — | 带版本与正文出处的事实账本 |
| 生成单位 | 一次回答 | 一段 / 一章 | — | 一章一事务，校验后提交 |
| 失败处理 | 重新生成一遍 | 手工修改 | — | 检查点恢复，正式稿不被污染 |
| 承诺边界 | 不承诺篇幅 | 不承诺篇幅 | — | 只承诺验证过的篇幅（1 万字 / 8–10 章起） |
| 成本与归属 | 订阅 | 订阅 + 云端 | 平台内阅读 | 本地运行、自带 Key、作品留本机 |

一句话：通用 AI 卖「会写」，写作工具卖「作者的效率」，Tome Agent 卖「读者零门槛写出一部自洽的长篇」。

## 1.2 产品定义

| 模板 | 内容 |
| --- | --- |
| 对于 | 心里有想看的题材、却不会写小说的普通读者 |
| 他们 | 想让 AI 把想法写成一部前后连贯的长篇，但通用 AI 一写长就「吃设定」 |
| Tome Agent 是一个 | 本地运行的长篇小说生成助手 |
| 它能够 | 用「逐章规划 → 正文 → 事实变更 → 独立审核 → 原子提交」维护带出处和版本的记忆，生成可暂停、可恢复、可导出 |
| 不同于 | 面向作者的复杂写作工作台，也不同于记不住设定的通用 AI 聊天 |
| 我们的产品 | 让不会写小说的人，也能创作出一部设定自洽、属于自己的长篇小说 |

## 1.2.1 解决的问题

1. **记不住设定**——年龄、关系、能力、地点，稍微写长就开始前后矛盾。
2. **时间线与因果对不上**——事件顺序、谁在场、发生过什么，跨章之后对不齐。
3. **伏笔与义务不回收**——前面埋的线索、答应过的走向，后面忘了提。
4. **上下文不可持续**——全文塞进长上下文：贵、注意力衰减；改成摘要：细节又丢了。
5. **生成过程不可恢复**——一次失败就要重来，成本和进度一起损失。

根因判断：**「记忆能力」≠「上下文长度」**。模型不是不想记，是「把前文再喂一遍」这种记忆方式撑不起一部书——越往后越贵、越模糊。所以我们不从「再写一段更长的提示词」入手，而从「怎么让故事状态可查、可验、可恢复」入手。

「状态记忆能减少跨章矛盾」目前是待验证假设：用同输入、同模型、有 / 无记忆的对照实验来证明。

## 1.2.2 对客户的价值（用户故事）

- **只想看自己想看故事的读者**：用一两句话描述题材、主角和走向，生成并读完第 1 章——不必等更新，也不必迁就平台现成的套路。
- **在意前后一致的连载读者**：每章后看到人物与物品的关键设定、版本，以及它从哪章开始、哪章改变——后文沿用同一设定，矛盾当场被指出。
- **业余写作者**：为一部作品填写文风要求与参考片段，设定从下一章开始生效——后续章节保持相近口吻，已经写好的正文不变。
- **想一次写完多章的作者**：设好目标章节数与字数，连续生成并在目标处停下——一口气拿到多章初稿，并知道写到哪里、为什么停下。

写法要求：用用户的业务语言，不出现实现词；每条故事配 Gherkin 验收条件，见 `docs/requirements/user_stories.md`（按 INVEST 拆分，共 5 条）。

## 1.2.3 解决方案：形态

选**本地网站**，不是小程序 / App：作品文件与 API Key 必须留在本机、成本按 token 透明、不经过上架审核；本地网页用浏览器即可打开，不需要账号、不需要装客户端。

| 组成 | 选型与版本 |
| --- | --- |
| 界面 | Vue 3.5.44 内置运行时，无前端构建步骤；本地服务 http://127.0.0.1:8765 |
| 编排 | LangGraph 1.2.17，把五个阶段建成状态图，支持条件分支与重规划 |
| 存储 | 文件模式零配置即可跑；需要持久化时用 PostgreSQL 17 + Psycopg 3.3.3 |
| 模型 | Chat Completions 兼容接口：DeepSeek、OpenAI 及其他兼容服务 |

用户看到的三件事：生成前显示预估 token 与人民币费用；生成中逐章保存检查点，中断可从断点继续；生成后可读章、导出排版好的 Markdown，作品目录在本机可备份。

## 1.2.3 解决方案：运行机制

一章的生成经过五个阶段、一次事务提交：

**下一章规划 → 正文候选 → 事实变更候选 → 独立审核 → 整章事务提交 → 导出 Markdown**

- **不越权**：规划只提下一章计划；写作角色不能直接改正式存档；审核角色只判不改。
- **可追溯**：每条事实带稳定属性名、版本、变更理由和正文原句，能查到某个设定从哪一章开始、又在哪一章改变。
- **可恢复**：先在副本上校验章节、计划与记忆，通过后整章提交；失败不改变正式快照，中断后从检查点继续。

## 2. 产品设计应用的原则

十二条原则，一条主线：每条都要能在仓库里找到证据。

### 组一：需求 · 信息 · 创新

| 原则 | 本产品的做法 |
| --- | --- |
| 需求原则 | 需求从「不会写」和「吃设定」出发，不是从「模型能干什么」出发；先冻结 MVP（单用户、本地、中文、顺序逐章），明确不做多人协作 / 移动端 / 自动出版；显需求 = 把想法变成第 1 章，隐需求 = 设定可查、失败可续 |
| 信息原则 | 设计前完成竞品与长文本架构调研（网文读者 5.75 亿、三类竞品对照、长上下文 / 摘要 / 检索方案比较）；结论「记忆能力是真实短板」写进问题定义，而不是拍脑袋定功能；调研、架构、验证记录都进仓库 |
| 创新原则 | 事件先行：先推演场景事件与状态，再写正文；事实账本：每条设定带稳定属性名、版本、变更理由和正文原句；提交是事务不是覆盖，在副本上校验通过才整体写入 |

### 组二：系统 · 收敛 · 优化

| 原则 | 本产品的做法 |
| --- | --- |
| 系统原则 | 写作被建成「规划—写作—记忆—审核—提交」的状态系统，用 LangGraph 状态图表达；四个角色职责与 JSON 契约固定；任何环节失败都不污染正式快照 |
| 收敛原则 | 记忆方案先发散四种（全文塞上下文 / 摘要压缩 / 向量检索 / 结构化事实），按「可核验、可恢复、成本」收敛到结构化事实 + 三层记忆；首版只带最近两章、最多 128 条有效事实 |
| 优化原则 | 篇幅按「总字数 − 已写 − 剩余章节」动态分配；局部失败降级保住有效正文；审核格式错误最多修一次，避免无限循环；重规划只改尚未写作的章节 |

### 组三：继承 · 效益 · 时间

| 原则 | 本产品的做法 |
| --- | --- |
| 继承原则 | 编排用 LangGraph、接口用 Chat Completions 兼容协议、界面用 Vue 运行时、存储用 PostgreSQL；继承状态图、事务提交、检查点恢复、幂等回执等成熟模式；不继承「面向作者的复杂工作台」形态 |
| 效益原则 | 本地运行 + 自带 Key + 按 token 计费，生成前显示预估人民币费用；单用户本地存档，省掉服务器与运维成本；社会效益：降低创作门槛，作品留在作者手里 |
| 时间原则 | 14 天交付计划：需求冻结 → 原型联调 → 真实模型 → 对照修复 → 交付演练；窗口期判断：通用模型记忆能力在增强，必须尽早用可复现对照实验证明价值 |

### 组四：定量 · 简化 · 审核

| 原则 | 本产品的做法 |
| --- | --- |
| 定量原则 | 成功标准写成可测指标（约 1 万字 / 8–10 章、跨章矛盾数对比基线、token 与费用、恢复成功率）；回归测试 127 项 + 长篇引擎 42 项；用户测试表逐项打分 |
| 简化原则 | 后端用 Python 标准库 http.server，不额外引入 Web 框架；前端用内置 Vue 运行时，零构建；文件模式零配置即可运行；首版只做中文 + 顺序逐章 + 单用户 |
| 审核原则 | 每章一个独立审核角色（硬矛盾、因果、记忆遗漏，只判不改）；提交前在副本上整体校验；PR 必须由另一名成员审阅；代码走 ruff 等质量检查，密钥与作品数据不进 Git |
