# Tome Agent 学生项目团队沟通管理与风险管理计划

> 本计划面向 4 人学生小组的软件创新课程作业。安排以课程截止时间、成员课余时间和现有开发能力为基础，优先保证项目可运行、材料可提交、过程可追溯。

## 一、项目概况

**项目名称：** Tome Agent——长篇小说生成助手  
**团队性质：** 4 人学生课程项目组  
**项目目标：** 基于 DeepSeek 模型，实现故事规划、逐章生成、跨章状态记忆、本地存档、继续生成和小说导出，完成可运行、可演示的软件作品及课程材料。

| 成员 | 主要职责 |
|---|---|
| 查军益 | 生成框架、模型接口与代码集成 |
| 秦宗鑫 | 项目协调、创作需求与小说质量评估 |
| 谭钧浩 | 环境安装、功能测试与问题跟踪 |
| 周涛 | 页面体验、文档整理与成果展示 |

成员共同参与需求讨论、软件试用和代码理解。每项主要交付物由负责人组织完成，并由至少一名其他成员复核，避免知识集中在一人手中。

## 二、沟通管理计划

项目日常沟通以微信群为主，代码和正式文档保存在 GitHub，任务与缺陷通过 Issue 记录。需要教师确认的课程要求，在课堂、课程平台或教师指定渠道沟通。沟通条目按照分析、设计、开发、测试、发布、运行维护和成果汇报的生命周期顺序排列；每项内容控制在能形成明确行动或交付物的粒度。

| 沟通内容 | 沟通频度 | 沟通方式 | 产出物 |
|---|---|---|---|
| 课程要求与需求分析：核对作业要求、目标用户、长篇创作痛点、首版范围和验收标准 | 项目启动时集中讨论；教师发布新要求或需求变化时即时沟通 | 课堂沟通、课程平台、微信群、GitHub Issue | 作业要求清单、问题定义、用户故事、验收标准、变更记录 |
| 产品与技术设计：创作流程、模块接口、记忆方案、存档方式和后续页面结构 | 开发前评审一次；重要设计变化时补充评审 | 课后面对面讨论、视频会议、屏幕共享、仓库文档评审 | 流程图、页面草图、架构说明、接口约定、设计决策记录 |
| 开发协作：任务认领、代码进度、接口依赖和阻塞问题 | 每日通过群消息简短同步；有共同空闲时间时集中联调；阻塞问题即时反馈 | 微信群、GitHub Issue、Pull Request、结对编程 | 任务看板、代码提交、评审记录、当日行动清单 |
| 测试验证：安装、模型调用、跨章衔接、事实记忆、存档和导出 | 每次功能合并后测试；每周至少一次集中交叉测试 | 同学互换电脑测试、问题复现演示、GitHub Issue | 测试用例、缺陷清单、复现步骤、测试报告 |
| 阶段检查与教师反馈：汇报已完成内容、当前困难和下一阶段安排 | 课程检查点或教师要求时；收到反馈后当日同步全组 | 课堂汇报、课程平台、教师指定渠道、组内复盘 | 阶段汇报、教师反馈记录、修改任务清单 |
| 发布与提交准备：版本范围、安装方式、演示流程、文档完整性和回退方案 | 每次提交或演示前检查；提交后复核一次 | 小组检查会议、GitHub 仓库、微信群 | 发布检查单、版本记录、安装说明、已知问题清单 |
| 原型运行维护：接口异常、调用用量、试用反馈和数据恢复 | 联调及试用期间每日查看；严重异常即时沟通 | 日志检查、微信群、GitHub Issue | 运行问题记录、用量记录、修复方案、更新后的用户手册 |
| 成果汇报：完成功能、测试证据、成员贡献与答辩分工 | 交付前集中整理；至少进行一次完整演练 | 小组会议、演示录屏、共享文档 | 答辩幻灯片、演示视频、贡献说明、项目总结 |

### 沟通执行规则

1. 日常同步只说明“已完成、下一步、遇到的阻碍”，减少无效会议；需要共同决策时再安排讨论。
2. 成员因上课、考试或其他课程任务无法按时完成时，应尽早在群内说明并重新分配任务。
3. 缺陷记录应包含运行环境、操作步骤、预期结果和实际结果，必要时附脱敏截图或日志。
4. 影响核心生成流程、数据安全或提交时间的问题立即报告，由项目协调人组织处理。
5. 需求变化先评估工作量和课程截止时间，再决定本次实现或放入后续计划。
6. 代码通过分支和 Pull Request 协作，合并前由另一名成员检查；关键文档随代码同步更新。
7. API Key 不在群聊、截图、日志或仓库中传播，测试数据分享前检查是否包含敏感内容。

## 三、风险管理计划

风险是可能影响一个或多个项目目标的未来不确定事件。风险管理覆盖资源、项目管理、外部因素、技术和进度五个维度，目标是提高正面机会发生的可能性，降低负面风险的概率或影响，提高课程项目按时完成的可能性。

影响程度、工作量影响、进度和成本影响以及优先权均采用高、中、低三级。优先权综合考虑发生可能性、影响程度和处理时限；它不是对成员能力的评价。

### 1. 风险识别与分析

| 风险名称 | 所属维度（资源、项目管理、外部因素、技术、进度） | 风险说明 | 影响程度（重要性） | 对工作量的影响 | 对进度和成本的影响 | 优先权（紧急程度） | 跟踪频率 |
|---|---|---|---|---|---|---|---|
| 成员开发经验不足 | 资源 | 成员可能在环境配置、调试和 Git 协作中遇到困难，造成返工。 | 高 | 高 | 高 | 高 | 每日 |
| 课程与考试时间冲突 | 资源 | 其他课程、作业或考试可能压缩共同开发和联调时间。 | 高 | 中 | 高 | 高 | 每周；交付前每日 |
| 模型调用预算不足 | 资源 | 长文本生成需要多次请求，学生可用经费可能不足以支持反复试验。 | 高 | 中 | 高 | 高 | 每次真实调用后 |
| 分工与接口约定不清 | 项目管理 | 任务可能遗漏或重复，成员完成的模块可能无法直接集成。 | 中 | 高 | 中 | 中 | 每日 |
| 需求理解偏差或范围扩张 | 项目管理 | 对作业要求理解不一致，或临时增加登录、多模型等功能，可能偏离评分要求并挤占时间。 | 高 | 高 | 高 | 高 | 每次需求变化时 |
| API Key 或作品数据泄露 | 项目管理 | 配置文件、截图或日志可能被误传到仓库或群聊，造成费用和隐私风险。 | 高 | 中 | 高 | 高 | 每次提交与分享前 |
| DeepSeek 服务或校园网络异常 | 外部因素 | 限流、超时、余额、接口变化或网络不稳定可能中断测试和演示。 | 高 | 中 | 高 | 高 | 每次联调和演示前 |
| 输入资料与测试用例不足 | 外部因素 | 故事设定、系统提示和跨章测试样例不足，可能无法充分验证长文本一致性。 | 中 | 中 | 中 | 中 | 每轮测试前 |
| 多角色输出不稳定 | 技术 | 模型可能返回格式错误、无效引文或遗漏事实变化，使章节候选无法通过审核。 | 高 | 高 | 高 | 高 | 每轮集成测试 |
| 长文本连贯性不足 | 技术 | 跨章可能出现人物、时间或物品状态矛盾，以及情节重复或推进停滞。 | 高 | 高 | 高 | 高 | 每批生成后 |
| 存档与版本冲突 | 技术 | 异常退出、并发写入或版本不一致可能造成进度丢失、正文与记忆不一致。 | 高 | 高 | 高 | 高 | 每次相关改动后 |
| 不同电脑安装失败 | 技术 | Python 版本、路径或系统环境差异可能导致同伴无法运行项目。 | 中 | 中 | 中 | 中 | 每次发布前 |
| GitHub 或第三方平台不可用 | 外部因素 | 仓库、Issue 或依赖服务短时不可访问，可能影响协作和提交。 | 中 | 低 | 中 | 中 | 每次提交前 |
| 交付准备时间不足 | 进度 | 开发或修复超时可能压缩文档整理、测试、录屏和答辩演练时间。 | 高 | 高 | 高 | 高 | 每日 |
| AI 辅助效率机会未充分利用 | 项目管理 | 若没有合理使用 AI 辅助代码草稿、测试和文档整理，可能增加重复劳动；未经成员复核又可能引入错误。 | 中 | 中 | 中 | 中 | 每周 |

### 2. 风险应对计划

| 风险类别 | 应对措施 | 主要负责人 |
|---|---|---|
| 经验与时间 | 提供统一安装说明和演示；把任务拆成半天到一天可完成的小项；关键操作结对完成；根据课表提前预约联调时间。 | 查军益、全体成员 |
| 模型费用 | 先用离线演示和短章节测试；设置调用次数和费用上限；记录每次用量；完成小规模闭环后再扩大篇幅。 | 查军益 |
| 分工与范围 | 每项任务指定负责人、截止时间和验收条件；公共接口变化先通知相关成员；新增需求先与作业评分要求比较。 | 秦宗鑫、查军益 |
| 密钥与数据 | 密钥只放本地 `.env`；启用 Git 忽略；提交和截图前检查；一旦泄露立即撤销并更换。 | 秦宗鑫、周涛 |
| 外部依赖 | 演示前检查 DeepSeek 余额、网络和 GitHub 状态；保留离线样例、测试结果和演示录屏，网络异常时使用离线材料说明。 | 谭钧浩、秦宗鑫 |
| 模型输出与连贯性 | 使用明确的 JSON 契约、证据校验和有限格式修复；从三章闭环开始测试；每批结果由两名成员按一致性清单复核。 | 查军益、秦宗鑫、谭钧浩 |
| 存档与安装 | 使用原子保存、写入锁和版本校验；候选失败时不修改正式状态；在另一名成员电脑上从零安装并保留备份。 | 周涛、谭钧浩 |
| 交付延期 | 优先保证核心闭环、测试证据和必交文档；提前准备 README、录屏和答辩材料；至少预留最后一天做演练和修复。 | 秦宗鑫、全体成员 |
| AI 辅助机会 | 用 AI 处理代码草稿、测试建议和文档整理，但所有输出必须由成员理解、运行和复核后才能提交。 | 全体成员 |

### 3. 外部依赖检查

1. 项目不依赖外部组织的资金或决策批准，但需要遵守教师给出的课程要求和提交安排。
2. 主要输入资料包括故事构想、系统提示、测试样例和课程模板；每次阶段测试前检查是否齐全、可用。
3. 项目较依赖 DeepSeek 接口、校园网络和 GitHub；因此保留离线演示、仓库本地副本和录屏作为替代方案。

### 4. 风险跟踪与升级

- 查军益维护风险台账，秦宗鑫在组内同步状态；风险状态分为“待观察、处理中、已缓解、已发生、已关闭”。
- 已发生的风险转为 GitHub Issue 或明确行动项，记录负责人、截止时间和验证结果。
- 密钥泄露、正式存档损坏、核心流程持续失败或可能错过课程截止时间时，立即通知全组并暂停非核心功能。
- 对高优先权风险优先处理；临近交付时先保证可运行、可测试、可演示和材料完整。
- 风险缓解后更新安装说明、测试用例、用户手册或演示方案，形成可追溯记录。
