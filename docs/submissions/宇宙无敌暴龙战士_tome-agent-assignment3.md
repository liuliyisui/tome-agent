# Tome Agent 产品团队沟通管理与风险管理计划

> 本文为拟定计划。提交前请将成员 A—D 替换为真实姓名，并由团队确认分工与沟通安排。

## 一、项目概况

**项目名称：** Tome Agent——长篇小说生成助手  
**团队规模：** 4 人  
**项目目标：** 基于 DeepSeek 模型，实现故事规划、逐章生成、跨章状态记忆、本地存档、继续生成和小说导出，形成可运行、可演示的软件作品。

| 成员 | 主要职责 |
|---|---|
| 查军益 | 生成框架、模型接口与代码集成 |
| 秦宗鑫 | 项目协调、创作需求与小说质量评估 |
| 谭钧浩 | 环境安装、功能测试与问题跟踪 |
| 周涛 | 页面体验、文档整理与成果展示 |

成员共同参与需求讨论、软件试用和代码理解；各项交付物由负责人组织完成，至少安排另一名成员复核。

## 二、沟通管理计划

团队以微信群进行日常沟通，以 GitHub 仓库保存代码和文档，以 Issue 记录任务、缺陷和待决策问题。影响需求、接口、进度的决定必须形成文字记录。

| 沟通内容 | 沟通频度 | 沟通方式 | 产出物 |
|---|---|---|---|
| 需求分析：目标用户、长篇创作痛点、首版功能范围与验收标准 | 项目启动时集中讨论；需求变化时及时沟通 | 团队会议、微信群、GitHub Issue | 需求说明、用户故事、验收标准、需求变更记录 |
| 产品与技术设计：创作流程、页面结构、模块接口、记忆与存档方案 | 开发前评审一次；重要设计变更时补充评审 | 屏幕共享、面对面讨论、仓库文档评审 | 流程图、页面草图、架构说明、接口约定、设计决策记录 |
| 开发协作：任务认领、进度、依赖关系和阻塞问题 | 每日一次约 10 分钟同步；阻塞问题即时反馈 | 微信群、GitHub Issue、Pull Request | 任务看板、代码提交、评审记录、当日行动清单 |
| 测试验证：安装问题、模型调用、跨章衔接、状态更新与恢复 | 每次功能合并后测试；每日集中汇总一次 | 交叉测试、问题复现演示、GitHub Issue | 测试用例、缺陷清单、复现步骤、测试报告 |
| 发布准备：版本范围、依赖安装、启动方式、演示与回退方案 | 每次发布前检查；发布后复核一次 | 发布检查会议、GitHub 仓库、群内通知 | 发布检查单、版本记录、安装说明、已知问题清单 |
| 运行维护：接口异常、用量、用户反馈和数据恢复 | 测试期间每日检查；严重异常即时沟通 | 日志检查、微信群、GitHub Issue | 运行问题记录、用量记录、修复方案、更新后的用户手册 |
| 成果汇报：完成情况、测试证据、成员贡献与答辩分工 | 交付前集中整理，并至少进行一次完整演练 | 团队会议、演示录屏、共享文档 | 答辩幻灯片、演示视频、贡献说明、项目总结 |

### 沟通执行规则

1. 每日同步围绕“已完成、下一步、遇到的阻碍”展开。
2. 缺陷记录必须包含运行环境、操作步骤、预期结果和实际结果，必要时附脱敏截图或日志。
3. 影响核心生成流程、数据安全或交付时间的问题即时报告，由负责人组织处理。
4. 需求变更先评估工作量和对交付的影响，再决定本次实现或延期，避免临近提交不断增加功能。
5. 代码通过分支和 Pull Request 协作，合并前由另一名成员检查；关键文档与代码同步更新。
6. API Key 不在群聊、截图、日志或仓库中传播，测试数据分享前检查是否包含敏感信息。

## 三、风险管理计划

风险管理覆盖资源、项目管理、外部因素、技术和进度。以下风险均为可能发生的事件，并非已发生的问题。

### 1. 风险识别

| 风险名称 | 所属维度 | 风险说明 |
|---|---|---|
| 成员开发经验不足 | 资源 | 成员可能在环境配置、调试和协作中遇到困难，增加返工与学习时间。 |
| 模型调用预算不足 | 资源 | 长文本生成和多轮工具调用可能消耗较多 token，影响后续测试与演示。 |
| 分工与接口约定不清 | 项目管理 | 任务可能遗漏、重复，或模块之间无法顺利集成。 |
| API Key 或作品数据泄露 | 项目管理 | 配置文件、截图或运行日志可能被误上传，造成费用损失或内容泄露。 |
| 需求持续扩张 | 项目管理 | 临时增加登录、多模型、复杂编辑等功能，可能挤占核心流程的开发时间。 |
| DeepSeek 服务或网络异常 | 外部因素 | 限流、超时、余额或接口变化可能导致生成中断，影响测试和演示。 |
| 多角色输出不稳定 | 技术 | 模型可能返回格式错误、无效引文或遗漏事实变更，使章节候选不能通过审核。 |
| 长文本连贯性不足 | 技术 | 跨章节可能出现人物、时间、物品状态矛盾，以及重复情节或推进停滞。 |
| 存档与恢复异常 | 技术 | 程序异常退出、文件损坏或错误恢复可能造成进度丢失、正文与记忆不一致。 |
| 不同电脑安装失败 | 技术 | Python 版本、依赖或系统环境差异可能导致同伴无法启动软件。 |
| 交付准备时间不足 | 进度 | 开发或修复超时可能压缩文档、部署和答辩演练时间。 |
| AI 工具提高开发效率的机会未充分利用 | 项目管理（机会） | 若合理使用 AI 辅助编码、测试设计与文档整理，可能提前完成首版，增加验证时间。 |

|---|---|---|---|---|
| 成员开发经验不足 | 高 / 高 | 提供统一安装说明和示例；任务拆小；关键操作结对完成；每人熟悉至少一条完整使用流程。 | 查军益 | 每日 |
| 模型调用预算不足 | 中 / 高 | 先进行短篇幅、小批量测试；设置请求与 token 上限；记录用量；扩展测试前评估预算。 | 查军益 | 每次真实调用后 |
| 分工与接口约定不清 | 中 / 中 | 每项任务指定负责人和验收条件；修改公共接口前通知相关成员；关键改动交叉复核。 | 查军益 | 每日 |
| API Key 或作品数据泄露 | 中 / 高 | 使用本地 `.env`；配置 Git 忽略规则；提交前检查文件；若发生泄露，立即撤销密钥并更换。 | 秦宗鑫，周涛 | 每次提交与分享前 |
| 需求持续扩张 | 高 / 高 | 冻结首版范围；新增需求先评估成本；优先保证规划、生成、记忆、审核、存档和导出可用。 | 查军益 | 每次需求变更时 |

| 多角色输出不稳定 | 高 / 高 | 使用明确的 JSON 契约、证据校验和有限格式修复；保留失败审计；先验证三章闭环，再扩大篇幅。 | 秦宗鑫，谭钧浩 | 每轮集成测试 |

### 3. 风险跟踪与升级

- 查军益 维护风险台账，每日同步风险状态、负责人及下一步行动。
- 风险状态分为“待观察、处理中、已缓解、已发生、已关闭”；已发生的风险转为具体问题跟踪，不能只停留在风险描述。
- 密钥泄露、正式存档损坏、核心生成流程持续失败等情况，立即通知全体成员并暂停相关操作。
- 对高影响风险优先处理；临近交付时优先保证可运行、可恢复、可演示，再安排扩展功能。
- 处理完成后记录原因、措施和验证结果，并更新安装说明、测试用例或应急方案。
