# Tome Agent 问题定义与产品描述

## 一、问题定义

长篇小说写作需要持续维护人物状态、事件因果、世界设定和后续伏笔。普通聊天式生成通常只依赖当前上下文；随着章节增长，早期事实容易被截断或忽略，从而出现人物信息前后矛盾、伏笔遗忘、情节重复等问题。同时，初学者团队需要一个能够本地运行、操作简单、生成过程可保存和恢复的原型，便于演示与验证。

Tome Agent 要解决的核心问题是：**如何让生成式模型在逐章创作长文本时，持续使用可追踪的故事状态，并在失败后继续工作。**

## 二、5W1H 分析

| 维度 | 回答 |
| --- | --- |
| What（做什么） | 开发一个面向长篇小说的写作 Agent。它先生成分层大纲，再调用 DeepSeek 创作，同时读写人物、事件、伏笔和事实账本；用户可控制本次生成的章节数、查看状态并导出作品。 |
| Why（为什么） | 解决长文本生成中上下文有限、设定遗忘、跨章矛盾、过程不可恢复和结果难追踪的问题，为小说作者提供可控的创作辅助。 |
| Who（为谁） | 首要用户是有故事构想但需要辅助扩写的网络小说作者、写作爱好者和学生创作者；本课程中的直接使用者是项目组与参与测试的同学。 |
| When（何时使用） | 在小说立项、生成大纲、逐章创作、暂停后续写、检查跨章一致性以及导出完整稿件时使用。 |
| Where（在哪里） | 第一版运行在用户自己的 Windows 电脑，通过本地 Streamlit 网页访问；模型请求发送到 DeepSeek 官方接口，作品检查点保存在本地。 |
| How（如何实现） | 使用“分层规划 → 逐章工具循环 → 事实与叙事状态更新 → 原子检查点 → 继续下一章”的流程。前端负责作品创建与操作，服务层负责调度，核心引擎负责工具调用、校验、记忆和恢复。 |

## 三、产品描述

### 3.1 产品名称

Tome Agent——面向长篇小说生成的写作助手。

### 3.2 产品目标

在一个可演示的本地应用中，将用户的故事构想转化为章节大纲和连续正文，并通过结构化故事记忆减少跨章遗忘。项目的创新重点放在长文本生成过程管理，而不是单次生成更华丽的文风。

### 3.3 核心功能

1. 根据书名、故事构想、章节数和目标字数生成四阶段规划与章节大纲。
2. 用户选择本次最多生成的章节数；系统内部按顺序逐章生成，并在每章成功后保存。
3. 维护人物状态、历史事件、未来义务和带版本及出处的事实账本。
4. 在失败时保留工作副本，允许用户显式恢复；正式正文只在章节通过完整校验后写入。
5. 在网页中查看大纲、正文和故事记忆，并导出 Markdown 或 JSON。

### 3.4 价值主张

- 对作者：降低人工反复查找前文和整理设定的负担。
- 对团队：提供清晰、可测试、可演示的长文本生成流程。
- 对课程：能够展示需求、设计、开发、测试、发布和项目管理的完整证据链。

### 3.5 最小可行产品范围

本轮交付聚焦单用户、本地运行、中文小说、DeepSeek 模型、顺序逐章生成和本地存档。不把多人实时协作、在线账户、移动端、自动出版和模型微调列入第一版。

### 3.6 成功标准

| 指标 | 第一轮目标 | 验证方式 |
| --- | --- | --- |
| 可运行性 | 新成员可按说明完成安装并启动页面 | 另一台电脑按 `setup.cmd`、`start.cmd` 实测 |
| 流程完整性 | 能完成创建作品、大纲、生成、保存、恢复、导出 | 端到端测试与现场演示 |
| 长文本能力 | 完成约 1 万中文字、8–10 章实验 | 保存正文、耗时与 token 记录 |
| 一致性 | 相比不使用状态记忆的基线，明确跨章矛盾更少 | 同输入、同模型对照测试，人工双人复核 |
| 工程质量 | 自动测试通过，密钥和作品数据不进入 Git | GitHub Actions 与仓库检查 |

“长文本一致性得到提升”目前是待验证假设，不能在完成对照实验前作为既定结论。

## 四、主要约束

- 团队 4 人，开发经验有限，需要优先完成可演示的最小闭环。
- DeepSeek 调用会产生费用，真实测试必须记录模型、参数、token 和成本。
- 第一版使用本地文件存档，同一本作品不支持多人同时编辑。
- 模型输出可能包含事实错误或不合适内容，最终正文仍需作者审核。
